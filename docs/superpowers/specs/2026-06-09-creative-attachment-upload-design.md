# Creative Attachment Upload — HTML-Derived Design

**Date:** 2026-06-09
**Branch/worktree:** `feat/creative-attachment-upload` / `plan42-worktree221`
**Status:** Design approved, pending spec review

## Problem

AI agents need to attach files they produce — html/markdown (LLM text), and binary
artifacts generated by tools (svg, png, mp4) — to a Creative so Collavre can serve
them and show them to the user. Two problems block this today:

1. **The MCP `creative_attach_files_service` reads files from server-local paths**
   (`file_paths` + `MCP_UPLOAD_ROOT` + `path_under?`). In production the MCP server
   is a remote container, so the agent's locally-produced file isn't visible to it.
   The only way to attach today is an out-of-band `scp` → `docker cp` into the
   container's upload root. This is the design defect tracked by Creative 13069
   ("업로드 경로가 서버 로컬만 허용").

2. **Two attachment inventories are disconnected.** `creative.files`
   (`has_many_attached :files`) is what `creative_list_attachments_service` reports,
   and is populated only by the MCP attach service. Separately, the Lexical editor
   embeds blobs directly into the description HTML (`<img>`, `<a download>`) via
   Rails ActiveStorage DirectUpload — those never land in `creative.files`. The two
   never sync.

## Goals

- An agent can attach an arbitrary local file (svg/png/mp4/etc.) it produced, via a
  CLI command, without any out-of-band copy into the server.
- Attached media is **embedded inline in the description HTML** so the user sees it
  in place when they open the Creative — including **inline mp4 playback**.
- `creative.files` is **fully derived from the description HTML** (single source of
  truth), so both editor uploads and agent uploads converge into one tracked
  inventory that `creative_list_attachments_service` reflects accurately.

## Non-goals (deliberately out of scope)

- **Absolute public-asset URLs.** Already solved by config: `public_asset_url`
  (`PublicAssetsHelper`) returns an absolute URL when
  `Collavre::IntegrationSettings.fetch(:public_assets_host)` is set. No code change
  here — populating that setting is an ops concern.
- **Large-video presigned S3 upload.** Multipart upload covers near-term svg/mp4.
  A presigned-PUT path for very large videos is a follow-up.
- **Agent file-read isolation.** Which local files an agent may read is the
  CLI/harness trust boundary, not the server's responsibility. The server only
  receives bytes and stores them.

## Key facts (verified in source, 2026-06-09)

- MCP service: `engines/collavre/app/services/collavre/tools/creative_attach_files_service.rb`
  — params `creative_id` + `file_paths`; reads via `File.open`; sandbox via
  `MCP_UPLOAD_ROOT`/`path_under?`; returns `{success, creative_id, attachments:[{signed_id, filename, content_type, byte_size, url}]}` with `url = public_asset_url(blob)`.
- Sibling MCP services: `creative_list_attachments_service.rb` (reads `creative.files`),
  `creative_remove_attachment_service.rb` (`signed_id` → `purge_later`).
- Lexical nodes: `engines/collavre/app/javascript/lib/lexical/image_node.jsx`
  (`exportDOM` → `<img>`), `attachment_node.jsx` (`exportDOM` → `<a download>`).
  **No VideoNode exists.** Both registered in `InlineLexicalEditor.jsx` (~lines 1001–1002).
- Upload plugin: `engines/collavre/app/javascript/components/plugins/image_upload_plugin.jsx`
  uses `@rails/activestorage` `DirectUpload`; URL/template injected in
  `_inline_edit_form.html.erb` via `data-direct-upload-url` (`main_app.rails_direct_uploads_path`)
  and `data-blob-url-template` (`main_app.rails_service_blob_path`).
- HTML→signed_id extraction: `engines/collavre/app/models/collavre/creative/describable.rb`
  `extract_signed_ids_from_description` (regex scans `/rails/active_storage/blobs/...`),
  currently called only from `purge_description_attachments` on `after_destroy_commit`.
- **Sanitizer (`describable.rb#sanitize_description_html`)** allows
  `Rails::HTML5::SafeListSanitizer.allowed_tags` + `table…`, `input`, with extra
  attributes `colspan`, `rowspan`, `download`, `data-filesize`, `type`, `disabled`,
  `checked`, `data-lexical`. **`<video>`/`<source>` and `controls` are NOT allowed**
  → a `<video>` node would be stripped on save unless the allowlist is extended.
- Bearer auth: `lib/mcp_oauth_middleware.rb` resolves
  `Doorkeeper::AccessToken.by_token` → `User.find_by(id: token.resource_owner_id)` →
  `Current.user`.
- Creatives controller: `engines/collavre/app/controllers/collavre/creatives_controller.rb`
  `creative_params` permits `:description, :progress, :parent_id, :sequence, :origin_id,
  :markdown_source, :content_type_input` — **`files` NOT permitted**.
- Routes: `engines/collavre/config/routes.rb` — `resources :creatives`; public asset
  route `get "/public-assets/blobs/:signed_id/*filename"`.
- CLI: `skills/collavre/scripts/collavre` — bearer token from local config; MCP over
  `/mcp/sse` + `/mcp/messages` (JSON-RPC). **No `attach` subcommand yet.**

## Architecture

```
Lexical editor (browser) ──DirectUpload (session+CSRF)──▶ blob ─┐
                                                                 ├─▶ description HTML embeds the blob node
CLI/agent ──multipart (bearer)──▶ new endpoint ──▶ blob ────────┘                       │ (on creative save)
                                                                                         ▼
                                              reconcile: creative.files := {signed_ids in description HTML}
```

The description HTML is the single source of truth. `creative.files` is derived.

## Components

### 1. Bearer multipart upload endpoint (agent/CLI door)

- Route: `POST /collavre/creatives/:creative_id/attachments` (nested under
  `resources :creatives`).
- New controller (e.g. `Collavre::Creatives::AttachmentsController`):
  - `skip_forgery_protection` — bearer-only, no cookie/CSRF path.
  - Reuses the Doorkeeper → `Current.user` → `creative.has_permission?(Current.user, :write)`
    chain. 401 if no/invalid token; 403 if not `:write`.
  - Accepts a single multipart file param; creates an ActiveStorage blob from the
    uploaded IO (`ActiveStorage::Blob.create_and_upload!` or attach to a holding
    record), content_type via `Marcel`.
  - Returns JSON `{ signed_id, filename, content_type, byte_size, url }` where
    `url = public_asset_url(blob)`.
- Multipart (not base64-over-JSON-RPC) so binary/large svg+mp4 transfer without the
  +33% base64 bloat or JSON-RPC message-size limits.
- The endpoint creates a blob only; it does **not** itself mutate `creative.files`.
  The CLI follows up by embedding the returned blob URL into the description (see §2),
  and reconcile (§4) attaches it on save. (Endpoint MAY also accept an
  `embed=true`/insertion mode later, but v1 keeps blob-creation and HTML-embedding
  separate for a clean boundary.)

> Open implementation detail for the plan: whether the new endpoint also performs the
> description-HTML embed server-side, or returns `{signed_id,url}` and lets the CLI/
> caller insert the node. Default: endpoint returns blob info; embedding is the
> caller's step. Resolve in writing-plans.

### 2. CLI `collavre attach`

- `collavre attach --creative <id> --file <path> [--file ...]` in
  `skills/collavre/scripts/collavre`.
- Reads the local file(s), POSTs multipart to the new endpoint using the existing
  bearer token from CLI config, infers content_type (Marcel-equivalent / by
  extension), prints the returned `url`/`signed_id` per file.
- The CLI is where "which local files may be read" lives — a harness/trust-boundary
  concern, intentionally outside the server.

### 3. VideoNode + sanitizer (inline mp4 — this scope)

- New `engines/collavre/app/javascript/lib/lexical/video_node.jsx`
  (DecoratorNode), `exportDOM` → `<video controls src=… >` (and `importDOM` to round-
  trip). Registered alongside ImageNode/AttachmentNode in `InlineLexicalEditor.jsx`.
- Upload plugin: route by content type — `video/*` → VideoNode, `image/*` →
  ImageNode, else AttachmentNode.
- **Extend `sanitize_description_html`** allowlist: add tags `video`, `source` and
  attributes `controls`, `src`, `type` (and any needed `width`/`height`/`preload`),
  or `<video>` is stripped on save.

### 4. Full derivation + reconcile on save

- On creative create/update (after description is sanitized/saved): call a reconcile
  step that:
  1. Extracts signed_ids from the saved description HTML (reuse
     `extract_signed_ids_from_description`).
  2. Sets `creative.files` to exactly that set: **attach** referenced-but-unattached
     blobs, **detach** attached-but-unreferenced blobs.
- Result: editor uploads (HTML-embedded) and agent uploads (HTML-embedded) both land
  in `creative.files`; `creative_list_attachments_service` reflects exactly what is
  visible in the description.
- Detach uses `purge_later` semantics consistent with the existing destroy-time
  cleanup, so removing a node from the description eventually purges the orphan blob.

### 5. Backfill migration (full derivation, your decision)

- Data migration: for each existing Creative whose `creative.files` include blobs
  **not** referenced in its description HTML, embed the corresponding node(s) into the
  description HTML (image → `<img>`, video → `<video>`, other → `<a download>`) so the
  switch to "HTML is source of truth" loses nothing.
- **Idempotent** (re-running embeds nothing already present) and **reversible** (down
  migration is a safe no-op or restores prior state). This is the highest-risk step
  because it rewrites stored description HTML; it must be guarded and tested before
  reconcile-driven detach goes live.

### 6. Retire path input on MCP `creative_attach_files_service`

- Remove `file_paths`, `MCP_UPLOAD_ROOT`, `path_under?`, realpath/outside logic — the
  server no longer reads server-local paths.
- The tool may continue to accept **inline LLM-generated text content** (html/markdown)
  if useful, attaching via the same embed+reconcile path; binary upload moves to the
  bearer HTTP endpoint. `creative_list_attachments_service` /
  `creative_remove_attachment_service` are unchanged in interface (they read/modify
  `creative.files`, now HTML-derived).

## Data flow (agent attaches an mp4)

1. Agent runs `collavre attach --creative 123 --file /tmp/out.mp4`.
2. CLI POSTs multipart to `/collavre/creatives/123/attachments` with bearer.
3. Endpoint checks `:write`, creates blob, returns `{signed_id, url, content_type:"video/mp4", …}`.
4. CLI (or a follow-up update) inserts a VideoNode-equivalent `<video src=url controls>`
   into Creative 123's description and saves.
5. On save, sanitizer keeps `<video>` (allowlist extended), reconcile extracts the
   signed_id and attaches the blob to `creative.files`.
6. User opens Creative 123 → mp4 plays inline; `creative_list_attachments_service`
   lists it.

## Error handling

- Upload endpoint: 401 (no/invalid bearer), 403 (no `:write`), 404 (creative not
  found / not visible), 422 (no file / unsupported), 413-style guard for oversized
  payloads (optional limit).
- Reconcile: must not raise on save for malformed HTML — extraction returns `[]`,
  reconcile becomes a no-op rather than blocking the save.
- Backfill: per-record failures logged and skipped, not fatal to the whole migration;
  re-runnable.

## Testing

- **Endpoint:** bearer required (401 without), `:write` enforced (403), multipart blob
  created + persisted, returns absolute-or-relative `url` per config, content_type
  inferred.
- **Reconcile:** add node → blob attached; remove node → blob detached; idempotent
  re-save (no churn); malformed HTML → no-op, save succeeds.
- **Backfill migration:** existing orphan `creative.files` get HTML nodes; re-run is a
  no-op; down migration safe; mixed image/video/other typed correctly.
- **VideoNode + sanitizer:** mp4 → `<video controls>` survives sanitize round-trip;
  svg/png → `<img>`; non-media → `<a download>`; sanitizer still strips disallowed
  tags.
- **CLI `attach`:** reads file, posts with bearer, prints url/signed_id; multi-file;
  error on missing file / unconfigured auth.
- **MCP service retirement:** `file_paths`/upload-root tests removed; remaining
  list/remove behavior intact.

## Risks

- **Backfill rewriting stored HTML** is the main risk → idempotent + reversible +
  tested on a copy before enabling reconcile-driven detach.
- **Reconcile detach is destructive** (purges orphan blobs). Ensure the backfill runs
  *before* detach is active so legacy files aren't purged for not being in HTML.
- **Sanitizer allowlist widening** (`<video>`/`<source>`) slightly enlarges the
  HTML-injection surface; scope to the specific tags/attributes needed and keep
  src/href validation.

## Decisions locked

- Inline mp4 playback: **yes, this scope** (VideoNode + sanitizer).
- `creative.files`: **fully derived from HTML, with idempotent/reversible backfill
  migration.**
- Bearer auth: **add a dedicated bearer-only upload endpoint** reusing Doorkeeper;
  Lexical keeps its existing session+CSRF DirectUpload.
- Scope: **single PR/worktree** (`plan42-worktree221`).
